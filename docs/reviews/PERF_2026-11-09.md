# Timings on the full catalogue (Phase 19, S6)

Measured on 9 November 2026, after B13, when the catalogue held all 84
interests (252 places and 168 experiences, legacy ones included).

## Method

- Android emulator (1080 × 2400, 420 dpi) running the dev client against the
  production JS bundle (`npx expo start --dev-client --no-dev --minify`).
- Each action is timed from a screen recording with touch dots on
  (`show_touches`): the first frame where the touch dot appears, then the
  first frame where the target region changes ("first") and the frame after
  which it no longer changes ("settle"). Median of three runs.
- The emulator was restarted before the final runs: after 21 hours of
  uptime its graphics service sat at full load and a first set of runs gave
  numbers that said more about the host than the app. Those runs are not
  used below.

## Results

| Action                                            | First (median) | Settle (median) | Runs (settle)    |
| ------------------------------------------------- | -------------- | --------------- | ---------------- |
| Filtre: tap → sheet with "Vis N resultater"       | ≤ 1 frame      | 0.23 s          | 0.07, 0.23, 0.24 |
| Sveip, first visit after a cold start: tap → card | 0.30 s         | 0.46 s          | 0.43, 0.55, 0.46 |
| Mode switch, For deg → Live: tap → pins           | 0.12 s         | 0.12 s          | 0.13, 0.07, 0.12 |
| Welcome, "Fortsett som gjest" → map with tab bar  | 0 s            | 1.2 s           | 1.18, 3.00, 0    |

The welcome screen's photo moves, so the last row is noisy; its spread
(0 to 3 s) is wider than the others.

## Compared with earlier phases

- Filtre took about 10 s to open in the dev build before 0319 and 5.6 s
  after it (Kategori rows mount on first open). In production on the full
  catalogue it settles in about a quarter of a second, within its 320 ms
  slide.
- The first Sveip visit took 0.5–1.7 s to settle in Phase 10 (14 places, 6
  experiences); with the full catalogue it settles in about half a second,
  since the deck builds nearest first and loads only the cards it shows.

## Outcome

No action above half a second except the first map after the welcome
screen, which includes building the catalogue and mounting the native map.
No code was changed in this slice. iOS and real phones were not measured.

# Speed pass: baseline (ledger 0344)

The user asked why the app is slow, stutters when dragging and sometimes
freezes or crashes, on the phone and on the emulator. The phone runs the
EAS development APK, which loads its JS, every photo and the fonts from
Metro over Wi-Fi.

## Method

- One signed-in session per run on the emulator (1080 × 2400, 420 dpi, 4 GB),
  driven by a script with adb input (`speed.sh` in the session scratchpad):
  - start: cold start, then sign in;
  - pan: twelve drags on the map;
  - sheet: open experience e1, drag to full, back to mid, close;
  - browse: expand the list, five flings, collapse;
  - Filtre: open, scroll to the price slider, drag it for 3 s;
  - Sveip: five swipes;
  - chat: type 32 characters in a thread.
- Per scenario:
  - `dumpsys gfxinfo` is reset before it: janky frames, frame percentiles, slow-UI-thread count;
  - CPU time per thread from `/proc` (JS thread `mqt_v_js`, main/UI thread, RenderThread, Mapbox's render thread, whole process);
  - `dumpsys meminfo` after it: PSS, native heap, decoded bitmaps.
- Frame numbers on this emulator are noisy. A system app (Settings) scrolls with 16 % janky frames and a 25 ms median, so treat that as the floor. They also drift as the emulator ages (one run of the same code got worse on every scenario after 7 hours of uptime). CPU time per thread measures work done, so before/after pairs use it, run back to back on a freshly booted emulator.
- Map pans do not appear in gfxinfo (Mapbox draws on its own surface); the CPU columns cover them.

## Memory

- Dev JS adds about 60–110 MB. Mapbox adds about 70 MB at start and about 150 MB by the end.
- About 450 MB of native memory stays unexplained in every mode. The preview (release) APK will show whether it belongs to the debug native build or to the emulator's GPU emulation.
- Memory is flat while the app sits idle.
- Opening the page sheet costs about 110–140 MB.

## Freezes and crashes

- The emulator's exit history for the day shows no low-memory kills.
- One ANR, "Input dispatching timed out" at 15:01 at 1.3 GB RSS. Its trace has the main thread waiting in `HardwareRenderer.syncAndDrawFrame` (the GPU sync for a frame), with the JS thread, Mapbox's render thread and the RenderThread idle. The main thread had used 266 s of system time, which is GL emulation.
- That freeze was the emulator's graphics stalling, not app code, though heavy screens give it more to draw.
- A startup ANR and a start timeout followed it.

## Still to measure

- The preview APK on the emulator: release native code and Hermes bytecode, no Metro. It waits for the EAS build, which needs the Mapbox tokens in the EAS preview environment.

## Targets for the end of the pass

- No ANR during the script.
- Less JS and UI-thread CPU in every scenario than in the table above.
- Less memory at the end of the script than in the table above.

# Speed pass: images (ledger 0349–0350)

The user asked to "optimize all the images" during the pass.

## What the app bundles

| Set                     | Files | Size    | Long edge                       |
| ----------------------- | ----- | ------- | ------------------------------- |
| Library photos, full    | 521   | 22.4 MB | median 800 px, at most 1,080 px |
| Library photos, small   | 521   | 9.0 MB  | 480 px                          |
| Portraits, full / small | 77    | 2.0 MB  | 600 px / 256 px                 |
| Sveip photos, full      | 12    | 0.9 MB  | 1,350 px                        |
| Sveip photos, small     | 12    | 0.2 MB  | 480 px                          |
| Kartlag previews        | 7     | 83 KB   | 480 px                          |

The blurred previews are 128 KB of data URIs inside the JS bundle. The app
icons (79 KB of PNG) are only read at build time.

## Findings

- Every photo is WebP at quality 75 with the slowest, best compression.
  Re-encoding 31 sample photos at quality 70 saved 6 % and at quality 62
  saved 12 %, with SSIM against the current files falling to 0.98–0.99.
  Only 60 photos still have their original JPEG in git history, so every
  other re-encode would compress an already compressed file. Rewriting about
  1,200 files would also add about 30 MB to the repository's history for
  good, to save 2–4 MB. Not done.
- expo-image shrinks each photo to the size of its view when it decodes it
  (`allowDownscaling`, on by default), so a smaller file would hardly
  change memory.
- Every small slot already loads the small file: avatars (through
  `Avatar`), rails, rows and thumbnails (`thumb`, `libThumb`,
  `smallImage`). No slot loaded a full photo where the small one would do.
- What cost memory and work was how many photos were decoded at once:
  - Each browse card decoded all of its photos up front (ledger 0349). It
    now decodes the first and the rest once someone swipes. After scrolling
    the list, bitmaps fell from 113 MB (97–100) to 61–66 MB (63–65), and
    PSS from 901–907 MB to 849–866 MB.
  - The photo viewer's list rendered up to ten photos when it opened
    (ledger 0350). It now renders the photo it opens at and its
    neighbours. Items carry at most three photos today, so on the emulator
    the difference is at most one photo and stays within the noise (54 MB
    of bitmaps with the viewer open, before and after).
- Three photos were bundled but used nowhere (`langrenn-3`,
  `market-vinyl`, `quiz-5`): 277 KB with their small files. Removed.

## Left for later

- Previews as thumbhash strings instead of 16 px WebP data URIs (about
  110 KB less JS) needs a new dev dependency. It is weighed with startup in
  ledger 0352.
- The map copies every pin image again 400 ms after it mounts, for the one
  pin drawn with SVG. Also weighed in ledger 0352.
- On the phone, the development build loads every photo from Metro over
  Wi-Fi. Only the preview APK removes that. The APK waits for the Mapbox
  tokens in the EAS preview environment.
